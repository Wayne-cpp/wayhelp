## 2026-10-07 brainstorm 定稿

- **我的关键原话**:「把客服系统的工具层从几个写死的内置工具,升级成即插即用的工具系统」;工具注册「一律带齐工具名、用途描述、JSON Schema 参数定义三样,登记进同一份工具表」;参数拦下「不抛异常了事,把校验错误说明包成一条工具结果回灌给模型」;权限「外部 MCP 工具的用途声明是对方自己写的、不可信……只认我们这侧的权限规则,不看 Server 声明、不让模型临场判断」;重试「只给网络抖动这类暂时性故障,业务空结果不重试,写操作默认不自动重试(超时未必没执行,重复执行比失败更糟)」;审计「被权限拒、被校验拦的调用同样要落;审计表不挂外键,写审计失败不许反过来拦工具执行」;MCP「Server 内部照第 2 章工具的做法随机生成 mock 数据返回」;确认流「照第 6 章订单选择器的做法用 LangGraph interrupt 把工单预览推给前端」;技术选型「MCP 官方 Python SDK,走 Streamable HTTP」「langchain-mcp-adapters 的 MultiServerMCPClient」定死。
- **关键产出**:路径裁定 Architectural;两路并行探索报告(现役 executor.py 已有 ToolRegistry/ToolExecutor/ToolExecutionRecord 雏形是升级挂点;build_graph_tools 每轮闭包绑定;ch06 interrupt/resume 全链可照抄;前端订单卡捕获式身份模式;mcp 与 langchain-mcp-adapters 两依赖均缺);两问澄清(①MCP 订单归属 → 拍板**客户端把门**,Server 纯 mock 不认用户;②动态发现节奏 → 拍板**每轮 get_tools() 现问现拿**,Context7 查实 MultiServerMCPClient 每次调用新建 session、天然无重连负担);方案三选一拍板**方案 A 进程内全局 ToolCatalog + 每轮工具面装配**(否掉 B 每轮临时构造增强版、C DB 工具表+注册 API);六节设计逐节获确认(架构与目录 / 执行引擎六步 / 审计 / MCP 接入 / 工单确认流 / 测试配置验收映射)。spec 落盘 docs/superpowers/specs/2026-10-07-ch08-tool-system-design.md。
