## 阶段 2:spec 评审与修订(2026-09-18)

**我的关键原话**:「spec我已经使用gpt6进行review并修改了」——评审由我用 GPT-6 完成,改动直接落在 spec 工作区(+159/-61)。

**AI 的关键产出**:本阶段 AI 无新产出物,职责是消化修订、核对内部一致性(工具集/路由表/State 字段/帧顺序/测试映射自洽,与定死选型无冲突)、提交归档。

**我拒绝/纠偏了什么**(本轮是用户方纠偏 AI 原设计,逐条记录):

1. **D4 收紧为「聊天 Agent 无建单权限」**:原设计让 Agent 保留 create_ticket(沿用 ch02 同事务置「已转人工」);修订后 create_ticket 与 query_faq 均退出聊天图绑定与执行注册表,Agent 只有 3 个只读业务工具 + suggest_options 伪工具,伪造 create_ticket 调用只回 unknown_tool;写 tickets 唯一通道是动作端点。
2. **新增 D6 needs_knowledge 分流**:分流键从「七类意图」升级为 `(intent, needs_knowledge)` 14 组合,知识需求优先于意图名称(混合问题、投诉+政策问都先检索);解析失败兜底从原设计的「售后→business fail-open」改为「售后+needs_knowledge=true→knowledge 保守检索」——fail-open 会绕过置信度闸,是原设计真 bug。
3. **检索故障与低置信分离**:NOTE_UNCONFIGURED/REBUILDING/REBUILD_REQUIRED/超时 → `KB_UNAVAILABLE_ANSWER` 不入池;零命中 → REFUSAL_ANSWER 入 `retrieval_low_conf`;高分但模型自评拒答 → 入 `self_check`。原设计把三类混在一个 low_confidence 分支。
4. **State 轮次生命周期表(§10.1)**:LangGraph 同 thread 未覆盖字段会延续,服务必须每轮显式构造全部临时字段初值——原设计只画 State schema 没定重置语义,有串轮污染隐患(evidence/建议按钮/入池标记串到下一轮)。
5. **suggest_actions 帧带 source_message_id**:`commit_turn` 返回本轮用户消息 ID,按钮绑定产生它的那条消息;动作端点必填 source_message_id 并校验归属,杜绝「点旧按钮给新问题建单」;字符串传输防 JS BIGINT 精度损失。原设计「取最近一条用户消息」在多轮后会错配。
6. **token 预算精细化(§7.2/§7.3)**:stream_usage=True 显式开启、调用前预留式预算、usage/estimated/mixed 标记、缺失 usage 不得按 0 计;DeepSeek 端点 stream_options 兼容性列入联调验证项。
7. **消息完整性**:validate_turn 扩展为逐组校验多步工具配对;commit 成功后才发 citations/suggest_actions;失败路径不提交、不发 [DONE]。
8. **验收标准 5→11 条**:新增故障不入池、State 串轮隔离、旧按钮建单正确性、预算前置生效、多步消息整体提交、Agent 零写权限六组验收。
9. 话术定稿:COMPLAINT_REPLY / CHITCHAT_REPLY / FALLBACK_ANSWER 修订,新增 KB_UNAVAILABLE_ANSWER / AGENT_BUDGET_ANSWER。

**翻车与返工**:无代码返工——修订全部发生在写代码之前,正是评审门的价值;原设计三处缺陷(fail-open 绕闸、Agent 持写权限、State 串轮)被拦在实现前。
