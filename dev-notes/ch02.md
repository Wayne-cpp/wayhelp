# Ch02 开发过程记录 —— 电商智能客服:Function Calling 工具链

## 阶段 1:Brainstorm 定稿(2026-09-10)

**用户关键原话**
- 「我要用 Superpowers 模式给现有的客服系统装上查数据的能力,用 Function Calling 让模型自己决定调什么工具——工具链要长在客服聊天本身,用户在聊天页问一句就能触发。」
- 「项目基建搭正式:FastAPI 加 SQLAlchemy 的分层骨架;Docker 起 MySQL;建四张表灌测试数据」
- 「query_order / query_product / query_logistics 演示起见在工具内部随机生成数据返回,不接真实接口、不建表」
- 「只做单轮调用:模型调一次工具就收敛」「本章不做:多轮自动循环的 Agent Loop、向量检索、RAG」
- 「聊天页面是例外,用 Vibe Coding 方式直接做,我描述效果你改」
- 「涉及具体库、框架、API 的用法,一律先用 Context7 MCP 查最新官方文档和接口定义再动手」
- 「上面点名的技术选型是定死的,实现中发现矛盾或走不通,停下来问我,不要自行换方案」
- 「我会写一张 ch02-ddl.sql 的表」——四张表 DDL 由用户手写提供

**澄清问答(AskUserQuestion 四轮)**
- 建表方式:用户先反问「Alembic / create_all 这两个具体是什么意思」→ 解释后用户表明会手写 ch02-ddl.sql → 选定 **initdb 自动执行**(DDL 文件挂进 MySQL 容器 `/docker-entrypoint-initdb.d/` 首启执行,零新依赖,DDL 文件是唯一事实源;不引入 Alembic)
- 测试数据库:用户选 **Docker MySQL 测试库**(与验收同构;fixture 建空库+逐测试清表),弃 SQLite 内存
- 内存 SessionStore:用户选 **DB 实现为主、内存保留**(ch01 的 59 个测试不动,新 store 单独配 MySQL 测试)
- 单轮编排:用户选 **手写编排**(第一次 astream 绑工具聚合,有 tool_calls 则执行+回灌,第二次 astream 不绑工具物理收敛);弃 LangGraph create_react_agent(为单轮引整个 LangGraph 不值)、AgentExecutor(官方已边缘化)

**我的关键产出**
- 路径分类:architectural(在 ch01 存量上加数据层+工具链子系统)
- 8 节设计:项目结构、数据表字段契约、工具层(注册/校验/超时重试)、单轮编排、SSE 契约扩展(tool_start/tool_end 帧)、前端徽章(Vibe Coding 例外)、测试与验收、依赖与 Context7 核对清单
- 关键设计点:`create_ticket` 的 conversation_id 由每轮工具工厂闭包注入(模型不用填);commit_turn 扩展为提交完整消息序列(含工具轨迹),仍只在成功后原子提交;faq seed 全表避开「邮费」二字以保证验收 3 的漏召回如实发生

**用户拒绝/纠偏**
- 用户手写 DDL 覆盖了我设计 §2 的字段契约:`conversations.id` 用 **BIGINT 自增**(我原提议 CHAR(36) UUID 保持 session_id 协议不变——被覆盖,session_id 改为数字字符串透传,schemas.py 的 UUID 校验放宽);字段名 `user_id`;会话/工单状态与工单类型用**中文枚举**;faq.question VARCHAR(512)
- 第一次设计确认提问被用户 dismiss(未作答),改纯文本等待;用户随后直接发来 DDL 文件代替回答
